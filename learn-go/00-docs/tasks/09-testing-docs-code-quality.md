# 09 测试 文档与代码质量任务文档

## 1. 文档目标

本阶段的重点是让项目从“看起来能跑”升级为“可以被证明可靠”。你需要建立测试体系、文档体系和最小质量门槛，避免项目在功能增加后失去可维护性。

## 2. 学习结果

- 能为核心逻辑设计测试方案。
- 能为接口、数据库和异步流程选择合适的测试层级。
- 能维护最基本的项目文档和质量规范。

## 3. 知识层次拆解

### 3.1 单元测试

你需要掌握 `testing`、表驱动测试、错误路径测试。

扩展说明：

- Go 的表驱动测试非常适合覆盖多输入、多边界的函数。
- 单元测试重点在于快速验证业务规则，而不是替代所有集成验证。

### 3.2 集成测试

你需要掌握数据库、Redis、HTTP 组合行为测试。

扩展说明：

- 只做单元测试不足以验证真实后端项目，因为很多问题发生在组件交互处。
- 集成测试应优先覆盖事务、鉴权、缓存回源、异步任务状态流转等关键链路。

### 3.3 接口测试与 `httptest`

你需要掌握 handler 级测试、路由测试、响应断言。

扩展说明：

- handler 测试可以帮助你稳定验证参数校验、状态码、响应格式。
- 这类测试对接口规范的长期稳定很重要。

### 3.4 文档体系

你需要至少维护：

- `README.md`
- `.env.example`
- API 文档
- 数据库设计文档
- 部署说明
- 错误码文档

扩展说明：

- 文档的价值不是“为了好看”，而是为了减少后续自己和他人的理解成本。
- 一个能运行但没人看得懂如何启动的项目，工程价值是很低的。

### 3.5 质量门槛

你需要建立最小门槛：

- 提交前跑测试。
- 关键模块有测试覆盖。
- 主要错误码有文档。
- 接口变更同步更新文档。

## 4. 任务拆解

### 任务 1：为 service 层补测试

要求：

- 至少覆盖正常路径、异常路径、边界条件。

目标：

- 让核心业务规则可验证。

### 任务 2：为 handler 层补 `httptest`

要求：

- 覆盖参数错误、鉴权失败、成功响应。

目标：

- 稳定接口行为。

### 任务 3：补集成测试

要求：

- 至少选择数据库事务或异步任务状态流转做一条集成测试。

目标：

- 验证多组件协作。

### 任务 4：补项目文档

要求：

- 完成启动方式、环境变量、主要接口和数据库说明。

目标：

- 让项目具备可交接性。

## 5. 产出物

- 一组单元测试和集成测试。
- 一套最小文档集合。
- 一份测试策略说明。

## 6. 验收标准

- 能解释哪些逻辑适合单元测试，哪些更适合集成测试。
- 关键服务不再完全依赖手工点接口验证。
- 新人拿到项目后能按文档启动服务。
- 项目有清晰可执行的质量检查流程。

## 7. 下一阶段衔接

测试和文档体系形成后，就进入 `10 部署 / Docker / Linux / CI/CD`，把本地工程变成真正可发布、可运行、可重复交付的服务。
