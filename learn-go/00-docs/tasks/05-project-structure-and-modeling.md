# 05 项目结构 分层架构与业务建模任务文档

## 1. 文档目标

本阶段的重点是避免项目在功能增长后迅速失控。你需要学会分层、建模、职责切分和依赖组织，让代码可以继续演进，而不是变成一个巨大的 `main.go` 或超长 handler。

## 2. 学习结果

- 能设计清晰的 handler、service、repository 边界。
- 能判断某段逻辑应该放在哪一层。
- 能用结构体和领域对象表达核心业务模型。

## 3. 知识层次拆解

### 3.1 分层职责

你需要掌握 handler、service、repository、model、middleware、config 的职责划分。

扩展说明：

- handler 负责处理输入输出，不负责核心业务决策。
- service 负责业务流程和规则编排，是最常承载复杂逻辑的一层。
- repository 负责数据访问，隐藏数据库细节和查询实现。
- middleware 负责认证、日志、请求 ID、限流等横切逻辑。

### 3.2 业务建模

你需要掌握实体、DTO、领域对象、输入输出对象之间的区别。

扩展说明：

- 数据库模型、接口响应模型、业务领域模型不一定完全相同。
- 过度复用同一个结构体会让边界模糊，后续修改会互相牵连。
- 好的建模应当让业务规则有明确落点。

### 3.3 依赖组织与注入

你需要掌握如何把数据库、日志器、配置和外部客户端注入到服务中。

扩展说明：

- 依赖注入不等于引入复杂框架，很多 Go 项目用显式构造函数就足够了。
- 显式依赖比隐藏全局变量更利于测试和维护。

### 3.4 错误分层

你需要掌握不同层的错误如何表达和转换。

扩展说明：

- repository 层更关注数据库错误和资源不存在。
- service 层更关注业务规则错误、权限错误、状态冲突。
- handler 层负责把内部错误映射为 HTTP 错误响应。

### 3.5 可维护性意识

你需要理解：

- 为什么不要在 handler 里直接写 SQL。
- 为什么不要把事务边界散落在多个地方。
- 为什么模型命名、包结构、接口粒度会直接影响维护成本。

## 4. 任务拆解

### 任务 1：重构现有 API 目录结构

要求：

- 增加 `cmd`、`internal/service`、`internal/repository`、`internal/transport/http` 等目录。

目标：

- 从单层代码迁移到分层代码。

### 任务 2：梳理一条完整业务链路

要求：

- 选择“创建书签”或“更新 Todo”流程。
- 从 handler 到 service 再到 repository 逐层拆开。

目标：

- 训练职责拆分，而不是只拆目录不拆逻辑。

### 任务 3：设计领域模型与 DTO

要求：

- 区分请求结构、响应结构、数据库结构、领域结构。

目标：

- 提升边界清晰度，避免结构体滥用。

### 任务 4：统一错误模型

要求：

- 定义一套内部错误类型或错误码。
- 明确不同层的错误转换规则。

目标：

- 为后续认证、安全、异步任务等复杂流程打基础。

## 5. 产出物

- 一版清晰分层的项目结构。
- 至少一条完整业务链路的重构结果。
- 一份分层职责说明。

## 6. 验收标准

- 能判断某段逻辑应放在 handler、service 还是 repository。
- 能解释为什么某个规则不应该写在中间件里。
- 项目目录不再依赖一个超大入口文件。
- 新增功能时能自然找到扩展位置。

## 7. 下一阶段衔接

完成分层之后，就进入 `06 认证 / 鉴权 / 安全`。这时你已经有足够的结构承载登录、中间件、权限和安全策略，而不会把安全逻辑写得四处散落。
