# 03 HTTP REST Web 服务任务文档

## 1. 文档目标

本阶段要把你从“写 Go 程序”推进到“写可调用的后端服务”。重点不是先学框架，而是先理解 HTTP、接口设计、请求处理流程和统一响应规范。

## 2. 学习结果

- 能使用标准库或轻量框架写出基础 API。
- 能设计清晰的 REST 风格接口。
- 能处理请求参数、响应结构、状态码和统一错误。

## 3. 知识层次拆解

### 3.1 HTTP 基础

你需要掌握请求、响应、方法、头部、状态码、URL、查询参数、请求体。

扩展说明：

- 后端不是“收到请求就返回 JSON”这么简单，HTTP 本身就是一套契约。
- `GET`、`POST`、`PATCH`、`DELETE` 的语义要明确，不要混用。
- 状态码不只是给浏览器看的，更是前后端协作和排障的重要线索。

### 3.2 net/http 与路由

你需要掌握 `net/http`、路由注册、中间件基础。

扩展说明：

- 标准库先学扎实，后续切到 `chi` 或 `Gin` 成本很低。
- 路由本质是在做“路径 + 方法”到处理函数的映射。
- 中间件是后端横切逻辑的入口，后面认证、日志、限流都会依赖它。

### 3.3 JSON API 设计

你需要掌握 JSON 编解码、统一响应结构、错误响应结构。

扩展说明：

- 成功响应和错误响应都要稳定，不要今天返回字符串、明天返回对象。
- 统一格式的核心价值是便于前端消费、便于日志分析、便于接口文档维护。
- 错误响应最好包含机器可识别的错误码，而不是只有自然语言描述。

### 3.4 参数处理与校验

你需要掌握路径参数、查询参数、请求体参数、基础参数校验。

扩展说明：

- 参数校验是接口边界的第一层防线，不能把非法输入原样放进业务层。
- 你要区分“参数缺失”“参数格式错误”“资源不存在”“业务冲突”等不同失败类型。

### 3.5 分页、排序、筛选与版本管理

你需要掌握分页设计、排序字段、筛选参数、接口版本前缀。

扩展说明：

- 列表接口通常不是简单返回全部数据，分页是默认能力而不是附加能力。
- 版本前缀如 `/api/v1` 可以降低未来改动对客户端的破坏性。
- 排序和筛选设计不合理，前端和数据库层都会被拖累。

## 4. 任务拆解

### 任务 1：Hello API

要求：

- 用 `net/http` 写一个最小可用接口。
- 返回标准 JSON 响应。

目标：

- 先打通请求到响应的完整链路。

### 任务 2：Todo API v1

要求：

- 支持创建、查询列表、查询详情、更新、删除。
- 先使用内存存储。

目标：

- 练习 CRUD 接口、状态码和基本数据流。

### 任务 3：统一错误响应

要求：

- 定义错误码、错误消息、错误详情结构。
- 参数错误和业务错误分开处理。

目标：

- 建立接口层规范意识。

### 任务 4：接口测试与文档

要求：

- 用 `curl` 或 `httptest` 覆盖主要接口。
- 输出一份基础接口说明。

目标：

- 让 API 不只“能跑”，还“能被别人稳定使用”。

## 5. 产出物

- 一个可运行的 Todo API。
- 一套统一响应格式。
- 一份接口调用示例。

## 6. 验收标准

- 能用 `curl` 调通全部接口。
- 能返回合理状态码。
- 能处理参数错误和资源不存在。
- 能解释为什么某个接口用 `PATCH` 而不是 `POST`。

## 7. 下一阶段衔接

当 HTTP API 已经能稳定工作，下一步就该进入 `04 数据库 / SQL / 事务 / 索引`，把数据从内存搬到真实持久化存储。
