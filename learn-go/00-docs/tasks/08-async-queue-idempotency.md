# 08 异步任务 消息队列与幂等任务文档

## 1. 文档目标

本阶段的重点是理解什么事情不该阻塞在用户请求里，以及如何把耗时任务可靠地放到后台执行。你需要学会设计任务状态、失败重试、幂等处理和最小可用的 worker 体系。

## 2. 学习结果

- 能把同步流程拆成异步流程。
- 能设计最小可用的任务状态机。
- 能处理重试和重复消费带来的问题。

## 3. 知识层次拆解

### 3.1 为什么需要异步

你需要识别适合异步的业务：

- 耗时不可控。
- 依赖第三方服务。
- 失败后需要重试。
- 用户不需要立刻看到最终结果。

扩展说明：

- 异步不是为了显得架构高级，而是为了把用户请求延迟和后台处理解耦。
- 发送邮件、图片分析、报告生成、导入导出都很典型。

### 3.2 队列与 Worker

你需要掌握生产者、消费者、任务载荷、队列积压、失败重试。

扩展说明：

- 生产者负责提交任务，worker 负责消费任务，这种拆分有助于水平扩展。
- 队列的价值不仅是解耦，也包括削峰和平滑处理能力。

### 3.3 任务状态机

你需要掌握 `pending`、`processing`、`completed`、`failed`、`retrying` 等状态设计。

扩展说明：

- 没有状态机的异步任务很快会失控，你会不知道任务现在在哪一步、失败了没有、还能不能重试。
- 状态流转应该有明确规则，而不是到处随意改状态。

### 3.4 幂等与去重

你需要掌握唯一请求 ID、唯一约束、消费记录、结果覆盖写等方案。

扩展说明：

- 消息重复投递是常态而不是异常，所以“重复消费也不出错”是基本要求。
- 幂等不是队列层自动提供的，需要业务层配合设计。

### 3.5 技术选择顺序

建议顺序：

- 先用 goroutine 和后台任务理解模型。
- 再用 Redis + worker。
- 然后学习 Asynq。
- 更复杂场景再看 RabbitMQ、Kafka。

## 4. 任务拆解

### 任务 1：实现最小后台任务

要求：

- 把一个耗时动作从同步请求中拆出来。

目标：

- 先理解“请求快速返回，后台继续执行”的基本模式。

### 任务 2：实现任务状态查询

要求：

- 创建任务时返回任务 ID。
- 提供任务状态查询接口。

目标：

- 让异步流程对用户可见、可追踪。

### 任务 3：实现失败重试

要求：

- 失败后按规则重试。
- 超过次数进入失败状态。

目标：

- 建立任务恢复能力。

### 任务 4：实现幂等保护

要求：

- 设计一个防重复消费方案。

目标：

- 防止 worker 重复执行造成脏数据或重复通知。

## 5. 产出物

- 一个基础任务队列或 worker 系统。
- 一套任务状态机。
- 一份幂等设计说明。

## 6. 验收标准

- 用户提交任务后不需要同步等待完成。
- 可以通过接口查询任务状态。
- worker 重启后任务不会无故永久丢失。
- 重复消费不会生成错误结果。
- 失败任务可按规则重试。
