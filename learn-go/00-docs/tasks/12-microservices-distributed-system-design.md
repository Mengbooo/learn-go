# 12 微服务 分布式与系统设计任务文档

## 1. 文档目标

本阶段不是要求你立刻把项目拆成微服务，而是建立架构判断力。你需要理解单体、模块化单体、微服务、异步解耦和分布式一致性之间的取舍关系，避免“为了高级而高级”。

## 2. 学习结果

- 能判断当前项目是否真的需要拆分。
- 能从业务规模、团队规模、发布频率、运维能力等角度看架构问题。
- 能设计模块化单体，并知道未来如何平滑演进。

## 3. 知识层次拆解

### 3.1 单体、模块化单体与微服务

你需要理解三者的差异和适用场景。

扩展说明：

- 单体不等于混乱，微服务也不等于先进。
- 模块化单体通常是小团队和早期产品更稳妥的选择。
- 微服务真正解决的是团队协作、独立发布和资源隔离问题，不是代码写多了就必须拆。

### 3.2 服务边界与拆分信号

你需要掌握判断边界的几个维度：

- 业务域是否清晰。
- 发布节奏是否不同。
- 数据耦合是否过深。
- 运维和监控是否跟得上。

扩展说明：

- 如果连单体内模块边界都没理清，直接拆服务通常只会把混乱分布式化。

### 3.3 RPC、gRPC 与服务通信

你需要掌握服务间同步调用和异步事件的基本思路。

扩展说明：

- gRPC 适合高性能、强契约、内部服务通信。
- 事件驱动适合解耦和最终一致性，但会增加状态追踪复杂度。

### 3.4 分布式问题基础

你需要掌握 CAP、BASE、最终一致性、重试、幂等、分布式锁、Outbox Pattern、Saga 的基本概念。

扩展说明：

- 分布式系统的难点不是“多几个服务”，而是失败变成常态、网络变得不可靠、一致性不再天然存在。
- 幂等、重试和状态补偿是分布式设计里的基础能力。

### 3.5 架构演进路径

建议顺序：

- 先写好单体。
- 做成模块化单体。
- 拆出独立 worker。
- 再按清晰边界拆出服务。

扩展说明：

- 这是风险更低、认知更稳的演进方式。
- 很多真实项目最有价值的不是“拆成微服务”，而是“先把单体做到清晰可维护”。

## 4. 任务拆解

### 任务 1：为当前项目做模块边界图

要求：

- 画出用户、内容、任务、通知、鉴权等模块边界。

目标：

- 在单体阶段先建立系统级视角。

### 任务 2：判断是否需要拆服务

要求：

- 从团队规模、发布节奏、性能瓶颈、运维能力角度给出结论。

目标：

- 训练架构判断，而不是套流行术语。

### 任务 3：设计一个可演进方案

要求：

- 给出当前模块化单体方案。
- 给出未来第一步最可能拆出的服务，例如 worker 或文件处理服务。

目标：

- 建立“先稳住，再演进”的设计习惯。

### 任务 4：做一次系统设计演练

要求：

- 以 Bookmark Manager 或 BemoLens Backend 为题，写需求澄清、核心实体、API、数据库、缓存、异步任务和权限方案。

目标：

- 把前 11 个阶段的能力整合成系统设计表达。

## 5. 产出物

- 一份模块边界与演进设计文档。
- 一次系统设计练习结果。
- 一份“是否需要微服务”的判断结论。

## 6. 验收标准

- 能解释为什么当前项目适合单体、模块化单体或微服务。
- 能指出拆分后会新增哪些复杂度。
- 能提出一个合理的第一步拆分对象。
- 能把前面各层能力整合进完整系统方案。

## 7. 收官建议

完成本阶段后，不代表学习结束，而是代表你已经具备了完整后端成长路径的骨架。接下来最重要的事情不是继续堆概念，而是反复做项目、上线、排障、复盘，把这些文档变成真实经验。
