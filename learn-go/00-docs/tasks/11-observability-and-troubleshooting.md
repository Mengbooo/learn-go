# 11 日志 指标 链路追踪与可观测性任务文档

## 1. 文档目标

本阶段的重点是让服务不仅能运行，还能被观察、被诊断、被排查。后端真正进入生产后，写功能只是一部分，定位线上问题同样重要。

## 2. 学习结果

- 能设计结构化日志和关键指标。
- 能用请求维度的信息定位一次调用链中的问题。
- 能回答“慢在哪里、错在哪里、影响了谁”这类线上问题。

## 3. 知识层次拆解

### 3.1 Logs、Metrics、Traces 三件套

你需要理解：

- Logs 解决“发生了什么”。
- Metrics 解决“整体状态怎么样”。
- Traces 解决“一次请求经过了哪些环节”。

扩展说明：

- 只打日志不做指标，你很难看系统整体趋势。
- 只看指标不看链路，你又很难还原单个请求到底卡在哪。

### 3.2 结构化日志

你需要掌握日志字段设计，例如时间、级别、请求 ID、路径、状态码、耗时、用户 ID、错误码。

扩展说明：

- 结构化日志的价值在于可检索、可聚合、可关联，而不是人眼读着舒服。
- 没有统一字段，后续做日志分析和问题回溯会非常痛苦。

### 3.3 指标体系

你需要掌握请求量、耗时、错误率、数据库连接池、Redis 延迟、任务成功率等基础指标。

扩展说明：

- 指标不是越多越好，先做和业务稳定性直接相关的指标。
- 请求耗时和错误率通常是最先建立的核心观察面。

### 3.4 链路追踪

你需要掌握 request_id、trace_id、上下游调用关联。

扩展说明：

- 在有数据库、缓存、第三方服务、异步任务的项目里，没有请求链路标识会很难定位问题。
- 哪怕暂时不完整接入 OpenTelemetry，也应该先把请求 ID 贯穿起来。

### 3.5 线上排查思路

你需要形成一套基本问题分析路径：

- 先确认影响范围。
- 再确认是单接口问题还是系统性问题。
- 再看慢在应用、数据库、缓存还是外部服务。
- 最后结合发布记录、错误日志和指标变化定位根因。

## 4. 任务拆解

### 任务 1：接入结构化日志

要求：

- 为所有请求记录统一日志字段。

目标：

- 让请求有最基本的可追踪性。

### 任务 2：增加请求指标

要求：

- 统计请求次数、耗时、状态码分布。

目标：

- 建立对服务整体健康度的观察能力。

### 任务 3：增加请求 ID / Trace ID

要求：

- 在入口生成或透传请求标识。
- 贯穿到日志和下游调用。

目标：

- 支持单次请求排查。

### 任务 4：设计报警与排障清单

要求：

- 至少定义错误率、请求超时、队列积压等关键报警点。

目标：

- 让可观测性从“看面板”升级为“发现异常后能行动”。

## 5. 产出物

- 一套结构化日志方案。
- 一组基础服务指标。
- 一份线上排查问题清单。

## 6. 验收标准

- 能根据日志定位某次失败请求。
- 能根据指标判断服务是否出现性能退化。
- 能区分应用层、数据库层和外部依赖层的问题迹象。
- 发布后出现异常时有明确排查入口。

## 7. 下一阶段衔接
