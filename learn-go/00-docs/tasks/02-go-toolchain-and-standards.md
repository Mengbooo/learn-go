# 02 Go 工具链与工程规范任务文档

## 1. 文档目标

本阶段的重点是把“会写代码”升级为“会按 Go 工程方式写代码”。你需要掌握项目初始化、模块管理、格式化、静态检查、测试执行和基础目录约定。

## 2. 学习结果

- 能独立初始化一个规范的 Go 项目。
- 能使用常见命令完成构建、运行、测试、整理依赖和静态检查。
- 能识别不符合 Go 工程习惯的目录结构和编码方式。

## 3. 知识层次拆解

### 3.1 Go Modules

你需要掌握 `go mod init`、`go mod tidy`、依赖升级、依赖清理。

扩展说明：

- `go.mod` 定义模块边界和依赖版本，是项目构建的基础。
- `go mod tidy` 不是可选动作，它会清理无用依赖并补全缺失依赖。
- 理解模块路径能帮助你后续设计仓库结构和包引用关系。

### 3.2 构建与运行命令

你需要掌握 `go run`、`go build`、`go install`、`go test`、`go clean`。

扩展说明：

- `go run` 适合开发期快速执行。
- `go build` 适合构建明确产物，后续 Docker 打包会经常用到。
- `go install` 更适合安装工具类程序。

### 3.3 格式化与静态检查

你需要掌握 `gofmt`、`goimports`、`go vet`、`staticcheck`、`golangci-lint`、`govulncheck`。

扩展说明：

- Go 社区对代码格式非常统一，`gofmt` 基本是默认约束，不建议手动对抗。
- `goimports` 除了格式化还会整理导入，比单纯 `gofmt` 更适合日常开发。
- `go vet` 和 `staticcheck` 关注潜在 bug，`golangci-lint` 更适合统一多种规则。
- `govulncheck` 解决的是依赖安全问题，不是语法正确性问题。

### 3.4 项目目录结构

你需要掌握 `cmd`、`internal`、`pkg`、`docs`、`scripts`、`migrations` 的职责。

扩展说明：

- `cmd` 放程序入口，不要把所有初始化都塞到 `main.go` 里。
- `internal` 表达“仅项目内部使用”的包边界，适合放业务代码。
- `pkg` 只有在你明确要对外复用时才考虑，不是默认选项。
- `migrations`、`docs`、`scripts` 这些目录能帮助项目从一开始就具备工程感。

### 3.5 工程规范意识

你需要建立下面这些习惯：

- 提交前格式化代码。
- 提交前跑测试。
- 依赖变更后执行 `go mod tidy`。
- 入口文件只做组装，不承载大段业务逻辑。
- 不在 handler 直接写 SQL，不在普通错误上滥用 `panic`。

## 4. 任务拆解

### 任务 1：初始化标准项目骨架

要求：

- 新建一个 Go 模块。
- 创建 `cmd/server`、`internal`、`docs`、`scripts` 等基础目录。

目标：

- 建立对项目骨架的直觉，不再从单文件程序起步。

### 任务 2：整理开发命令

要求：

- 记录常用的构建、运行、测试、格式化命令。
- 最好补一个简单 `Makefile` 或命令备忘录。

目标：

- 降低重复操作成本，为后续多服务项目打基础。

### 任务 3：接入基础代码检查

要求：

- 至少接入 `gofmt`、`go test`、`go vet`。
- 有余力可补充 `golangci-lint` 和 `govulncheck`。

目标：

- 建立“本地先发现问题”的习惯。

### 任务 4：做一次结构审查

要求：

- 对照已有小项目检查目录是否混乱、职责是否交叉。

目标：

- 学会从工程视角看代码，而不是只盯着功能是否能跑。

## 5. 产出物

- 一个标准的 Go 项目骨架。
- 一份常用命令清单。
- 一套最小可用的本地检查流程。

## 6. 验收标准

- 能解释 `cmd` 和 `internal` 的作用。
- 能解释为什么提交前要执行 `go test ./...`。
- 能独立清理依赖和修复格式问题。
- 能指出一个混乱项目结构的问题点。

## 7. 下一阶段衔接

当你已经能稳定初始化和维护一个基础 Go 项目，就可以进入 `03 HTTP / REST / Web 服务`，开始从工具链过渡到真正的后端服务开发。
