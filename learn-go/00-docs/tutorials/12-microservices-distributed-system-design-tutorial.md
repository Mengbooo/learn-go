# 12 微服务 分布式与系统设计教程

## 1. 这章最容易学偏的地方

很多人学到这里，会开始强烈想把项目拆成微服务。

但这章真正的重点不是“拆”，而是判断。

你要建立一个更成熟的顺序：

1. 先把单体做清楚
2. 再做模块化单体
3. 真的有边界和组织需求时，再考虑拆服务

---

## 2. 单体不等于落后

一个结构清晰的单体，往往比混乱的微服务更有工程价值。

单体的优点通常是：

- 开发简单
- 部署简单
- 调试简单
- 一致性处理简单

它真正的问题通常出现在：

- 模块边界混乱
- 团队协作互相踩
- 发布影响面过大

所以你第一反应不该是“拆服务”，而是“边界清楚了吗”。

---

## 3. 什么是模块化单体

模块化单体不是“所有代码放一个目录”，而是：

- 一个部署单元
- 多个清晰业务模块
- 模块之间通过明确接口协作

一个很常见的结构：

```txt
cmd/
  api/
  worker/
internal/
  user/
  bookmark/
  auth/
  task/
  notification/
  platform/
```

这里的重点是：

- 用户逻辑别散落到各处
- 任务逻辑别到处直接改状态
- 平台能力和业务能力分层

这通常是小团队最稳的第一阶段形态。

---

## 4. 什么信号说明可能要拆服务

可以先观察这些：

- 某个模块发布节奏明显不同
- 某个模块资源消耗特别重
- 团队已经分工明确且经常互相阻塞
- 单体内部边界已经很清晰
- 运维、日志、监控能力已经跟上

你要特别警惕一个错误信号：

“代码文件变多了，所以该拆微服务了。”

这通常不是充分理由。

---

## 5. 一个更现实的演进路径

建议顺序通常是：

```txt
简单单体
  ↓
模块化单体
  ↓
独立 worker
  ↓
拆出第一个边界明确的服务
```

例如书签系统里，第一批更可能拆出的不是用户服务，而是：

- 文件处理服务
- 异步扫描服务
- 报告生成服务

因为这类模块：

- 耗时长
- 资源特征明显不同
- 天然适合异步化

---

## 6. 服务间通信怎么想

### 6.1 同步调用

常见是 HTTP 或 gRPC。

适合：

- 需要立即拿结果
- 契约清晰
- 上下游耦合可接受

### 6.2 异步事件

常见是队列或消息流。

适合：

- 解耦
- 削峰
- 最终一致性

更现实的理解不是二选一，而是：

- 查实时数据多用同步
- 后台处理和通知多用异步

---

## 7. gRPC 的生态位

gRPC 更适合内部服务调用，而不是浏览器直接访问。

优点：

- 强类型契约
- 性能好
- 代码生成成熟

代价：

- 学习和调试成本更高
- 浏览器端不如 HTTP JSON 直观

所以学习顺序一般是：

```txt
HTTP JSON
  ↓
模块边界
  ↓
内部 RPC / gRPC
```

---

## 8. 分布式真正增加了什么复杂度

拆成多个服务后，复杂度不是线性增加，而是种类增加。

你会额外面对：

- 网络失败
- 超时
- 重试
- 幂等
- 数据一致性
- 链路追踪
- 发布协调

在单体里，一次函数调用失败只是本地失败。

在分布式里，一次远程调用失败可能是：

- 对方挂了
- 网络抖了
- 超时过短
- 对方成功了但响应没回来

这就是为什么“把问题分布式化”很危险。

---

## 9. 最终一致性怎么理解

在单体和单库里，你很多时候可以直接靠本地事务保证一致。

但一旦跨服务：

- 用户服务
- 订单服务
- 通知服务

你通常就不能再指望一个本地事务全包住了。

这时更常见的是最终一致性思路：

- 主流程先完成核心写入
- 事件异步通知其他服务
- 失败后重试或补偿

你要先接受一个事实：

分布式里“一定立即一致”往往代价非常高。

---

## 10. Outbox Pattern 和 Saga 的直觉

### 10.1 Outbox Pattern

适合“本地数据更新”和“发送事件”要尽量一起可靠发生。

最小思路：

1. 业务数据和 outbox 事件一起写进数据库事务
2. 后台程序再把 outbox 里的事件投出去

它解决的是：

数据库写成功了，但消息没发出去怎么办。

### 10.2 Saga

适合跨多个服务、每步都可能成功或失败的长流程。

核心直觉不是“大事务”，而是：

- 一步一步推进
- 失败时做补偿动作

这些概念你现在先建立直觉，不需要急着完全掌握实现细节。

---

## 11. 系统设计题该怎么答

如果让你设计一个 Bookmark Manager Backend，你至少应该能按这个顺序说：

1. 需求澄清
2. 核心实体
3. API 设计
4. 数据库表
5. 缓存
6. 异步任务
7. 权限
8. 可观测性
9. 演进路径

这比一开口就说“我会用微服务 + Kafka + Kubernetes”更成熟。

因为系统设计首先是在解决需求，而不是展示名词储备。

---

## 12. 一个更稳的架构判断模板

当你犹豫要不要拆服务时，可以先问自己：

### 业务边界清楚吗

如果单体内边界都不清楚，拆出来大概率只是把混乱复制多份。

### 团队真的需要独立发布吗

如果还是 1 到 3 个人开发，强拆服务通常收益有限。

### 运维能力够吗

如果日志、监控、CI/CD 都不成熟，微服务只会让排障更难。

### 性能瓶颈真的来自部署单元吗

很多瓶颈其实是 SQL、缓存、外部依赖，不是“服务没拆”。

---

## 13. 这一章建议你手敲的练习

### 练习 1：画模块边界

为当前项目画出用户、内容、任务、通知、鉴权模块。

### 练习 2：写拆分判断

回答当前项目为什么暂时不该拆，或者为什么该先拆出 worker。

### 练习 3：设计演进路径

从单体写到模块化单体，再写到第一步可能拆出的服务。

### 练习 4：做一道系统设计题

选择一个你熟悉的后端项目，按需求、API、数据、缓存、异步、权限、观测性完整写一版。

---

## 14. 这章学完的最低标准

你至少应该能做到：

- 解释单体、模块化单体、微服务的差异
- 说清楚什么信号才值得考虑拆服务
- 理解分布式会新增哪些复杂度
- 说出最终一致性、幂等、补偿的大致作用
- 对一个真实项目给出合理的演进路径判断

做到这里，你就不只是会写功能，而是开始具备架构判断力。
